- В репозитории нет Supabase SDK, SQL migrations, RLS, auth handlers, backend

- Оригинальные бренд-активы и Amani Melasti reference отсутствуют среди файлов проекта.

## 2. Архитектура расширения

Сохранить экраны и модели представления; вынести операции в асинхронные сервисы:
Auth, Projects, DailyReports, MonthlyReports, Files, Branding, PDF.
Существующий синхронный load/save целого DemoState нельзя просто заменить сетевым
вызовом: нужны проектные запросы, DTO, пагинация, mutations и версии записей.

Демо оставить отдельным адаптером/режимом, с синтетическими данными. Production
использует Auth + PostgreSQL + private Storage и никогда не подмешивает demo seed.
При ошибке production-подключения показывать ошибку; не переключаться незаметно
на демо. Production-файлы и сессии не хранить в общем demo localStorage.

Роли строго три: `Director / Admin`, `Project Manager`, `Site Manager`.
На сервере использовать стабильные enum-коды, в интерфейсе — эти названия.
Директор видит все проекты; PM и SM — только назначенные. PM утверждает daily,
SM создаёт/редактирует свои drafts и исправления в назначенных проектах, директор
управляет проектами/аккаунтами/назначениями/брендингом и утверждает monthly.
Не добавлять директору права изменения утверждённых документов или SM-права PM
только ради удобства; дополнительные исключения требуют явного решения владельца.

Предлагаемые группы таблиц:

- profiles, projects, project_memberships;
- daily_report_series, daily_report_revisions, manpower, activities, quantities;
- media_assets, report_photos, approval_events;
- monthly_reports, monthly_versions, monthly_work_packages, progress_points;
- monthly_source_snapshots, monthly_generated_sections, monthly_source_links;
- schedule_versions/imports, attachments, branding_versions;
- pdf_jobs, pdf_artifacts, append-only audit_events.

RLS защищает также дочерние строки. Роль и memberships нельзя менять через
self-service profile update. Переходы состояний — транзакционные RPC/server
operations с проверкой auth identity, project membership и версии документа.
DB constraints/triggers запрещают обход блокировки прямым UPDATE/INSERT/DELETE.
Service-role/secret key — только сервер; обычные пользовательские запросы не
должны массово обходить RLS через service role. RPC с elevated rights требуют
фиксированного search_path, минимальных grants и собственных проверок доступа.

## 3. Этапы и критерии готовности

### M1. Supabase: схема, вход и проектные права

**Зависит от:** согласования плана и доступного локального Supabase либо отдельно
разрешённого dev/staging-проекта. Production-сервисы не включать.

- Versioned SQL migrations, ровно три роли, memberships, индексы/constraints.
- Login/logout, восстановление доступа, SSR-сессии и защищённые маршруты.
- Создание/приглашение сотрудников директором без публичного self-sign-up с ролью.
- Private buckets: photos, documents, branding, report artifacts; Storage policies.
- Минимальные admin-экраны проектов, сотрудников и назначений; archive вместо
  физического удаления проектов с отчётами.
- Изолированные demo и connected modes; отсутствие демонстрационного seed в prod.

**Готово, когда:** анонимный запрос закрыт; пользователь проекта A не читает и не
меняет B через UI, REST, RPC или Storage; пользователь не повышает свою роль;
директор создаёт/архивирует проект и назначает сотрудника; service key отсутствует
в клиентских артефактах. Проверки выполняются в БД, а не только на кнопках.

### M2. Постоянные daily reports и серверный workflow

**Зависит от:** M1.

- Подключить существующие 10 секций к async repository, не заменяя форму заново.
- Autosave с debounce, состояниями Saving/Saved/Error, безопасными retry и
  optimistic concurrency; не терять пользовательский ввод при сетевой ошибке.
- Стабильные series/activity IDs, ревизии и дата/время операций на сервере.
- Submit → PM approve / revision required с обязательным комментарием.
- Проверка действительного существования даты/проекта, диапазонов чисел, длины
  текстов, количеств и допустимых переходов на сервере и в БД.
- Private uploads, подписи, порядок фото, progress/retry; оригиналы и thumbnails.
- Невозможность заменить/удалить файлы утверждённой ревизии в обход формы.

**Готово, когда:** отчёт доступен с другого устройства; конфликт двух редактирований
обнаруживается; утверждённый оригинал не меняется прямым API-вызовом; новая
ревизия сохраняет старую и полный аудит; SM не утверждает свои отчёты.

### M3. Месячная агрегация, PM review и immutable release

**Зависит от:** M2; исходные данные должны иметь устойчивые ID и единицы измерения.

- Выбор проекта и любого reporting month; календарные границы по Asia/Makassar.
- Автоматически собирать редактируемый черновик: achievements/работы, quantities,
  personnel-days, фото, deliveries, equipment, safety, issues/delays, mitigation.
- Детерминированные текстовые сводки без обязательных внешних AI/платных API.
- Выбирать последние утверждённые ревизии; новые drafts не вытесняют approved.
- Идемпотентные jobs/imports и уникальность согласованного site-day/series.
- Группировать одинаковые работы в читаемые разделы с provenance. Не удалять
  одинаковые по тексту записи за разные дни: это может быть реальная новая работа.
- Суммировать только incremental quantities с совместимыми единицами; cumulative
  readings обрабатывать отдельно. Не складывать м² с м³ и не называть personnel-days
  числом уникальных сотрудников. Не выдумывать corrective actions из отсутствующих данных.
- PM редактирует генерацию и подтверждает progress/curve values; изменения
  подтверждённых показателей требуют нового подтверждения. Процент общего
  прогресса никогда не вычисляется из числа daily reports.
- Regenerate показывает различия и не затирает правки PM без подтверждения.
- Submit фиксирует версии источников/фото/показателей/нарратива; директор утверждает
  именно этот снимок. Новый daily не меняет уже утверждённый monthly.
- Автосборка по выбранному периоду и повторяемая job-логика сначала проверяются
  локально; production scheduler активируется только с отдельным разрешением.

**Готово, когда:** fixtures с ревизиями, повторным запуском и повторным импортом
дают одинаковые суммы; повторяющиеся реальные работы не теряются; после release
новая daily revision не меняет документ; PM-правки сохранены и директор видит
точно подтверждённую версию.

### M4. PDF/Excel schedules и проектные риски

**Зависит от:** M2, базового M3; шаблон импорта предоставляется для рассмотрения.

- Private PDF schedules как версионированные приложения.
- Сначала документированный `.xlsx`-шаблон: work package ID, даты, baseline/updated,
  planned cumulative progress, единицы и версия формата. Legacy `.xls` и макросы
  не принимать молча; определить поддерживаемые форматы до реализации парсера.
- Ограничения размера/строк/ячеек, content validation, защита от ZIP bombs,
  внешних ссылок/формул; никакого исполнения макросов и автоматического доверия MIME.
- Preview ошибок/данных; явное подтверждение PM до применения плановых данных.
- Actual progress не извлекать автоматически из Excel/PDF; отдельно подтвердить PM.
- Milestones, deviations, risks, forecast и next-month plan редактируемы и версионируются.

**Готово, когда:** неверный файл ничего не меняет; повторный импорт не дублирует
строки; непроверенные данные не попадают в curve/release; PDF связан с версией отчёта.

### M5. Оригинальный брендинг и downloadable PDF

**Зависит от:** M3–M4 для полного месячного отчёта; оригинальных логотипов и
Amani Melasti reference для визуального соответствия. PDF-engine spike можно
начать после M2, до завершения всей агрегации.

- Сначала проверить исходные активы и согласовать короткий visual sample.
- Upload company/project logos и cover images с правами директора, проверкой
  содержимого; не встраивать произвольный непроверенный SVG/HTML в PDF renderer.
- Premium нейтральная brown/black/white палитра, локальные лицензированные шрифты,
  A4, читаемые таблицы, фото без искажений, повтор заголовков и page numbers.
- Предпочтительный renderer: server-side Chromium/Playwright поверх адаптированных
  существующих print-шаблонов, если целевой hosting поддерживает Chromium. Решение
  о runtime подтвердить до выбора deployment; платный PDF API не требуется.
- Защищённый download endpoint/job worker, ограничение ресурсов, auth повторно при
  запросе; renderer не должен открывать произвольные внешние URL (SSRF).
- Брендинг/фото/шрифты фиксируются в snapshot; готовый PDF имеет report number,
  version, approval identity/time, checksum и private artifact запись.
- Daily и monthly включают все секции Phase 2, QC/supporting documents, приложения;
  не включать неутверждённые daily в официальный monthly.

**Готово, когда:** PDF скачивается без print-dialog, длинные таблицы/фото пагинируются,
проверены empty/large reports, логотипы оригинальные; файл после утверждения
воспроизводим из зафиксированной версии и доступен только уполномоченным.

### M6. Мобильные сценарии и end-to-end/security проверки

**Зависит от:** инкрементально M1–M5; тесты добавляются вместе с каждым этапом.

- iPhone Safari, Android Chrome, tablet/desktop; camera uploads, поворот снимков,
  большие фото, слабая сеть, повтор запроса, истечение auth session.
- Cross-device persistence, assigned-project visibility, доступ каждой из 3 ролей.
- RLS/RPC/Storage integration tests, role-escalation и cross-project negative cases.
- Daily submit/revise/approve и monthly generate/review/confirm/approve/download.
- Проверка snapshot immutability, quantities deduplication и отсутствия двойного
  counting; PDF structure/page/visual tests.
- Проверить доступный Share API с fallback Download. Не включать офлайн-кэш
  конфиденциальных отчётов без отдельного спроектированного logout/cleanup/conflict flow.
- Сохранить существующие demo E2E. Для production E2E запретить случайное повторное
  использование dev-сервера: текущий reuseExistingServer требует корректировки в CI.

**Готово, когда:** security и functional suites проходят на чистой БД; основные
мобильные сценарии проверены на настоящих устройствах или явно отмечены как
непроверенные. Одного mobile viewport в Chromium недостаточно для заявления iOS-ready.

### M7. Документация окружения и подготовка deployment

**Зависит от:** M1–M6; deployment-цель обсуждается до окончательного выбора PDF runtime.

- Документировать публичные Supabase URL/publishable key и отдельные server-only
  admin/service secrets; значения вводить в secure settings, не в чат/репозиторий.
- `.env.example` только с именами/плейсхолдерами, migrations/seed для dev, bootstrap
  первого директора без встроенного пароля и production demo seed.
- Инструкция auth redirect URLs, HTTPS, migrations, private buckets, resource limits,
  worker/scheduler, logs, backup/restore, rollback и ротации ключей.
- CI: lint/typecheck/unit, clean build, DB/RLS integration, production-server E2E.
- Локальная приёмка и readiness report с известными ограничениями.

**Готово, когда:** из чистого разрешённого dev-окружения по инструкции поднимается
система с тестовыми аккаунтами; секреты не попадают в клиент/логи; план deployment
проверяем и содержит откат. Публичный deployment остаётся отдельным действием,
требующим подтверждения владельца.

## 4. Главные риски и меры

| Риск | Мера / проверка |
| --- | --- |
| UI-роль принимается за безопасность | Auth + DB RLS + RPC проверки; тестировать прямые запросы без UI |
| service-role обходит проектные ограничения | Только server-only admin operations; минимальная область применения, аудит |
| Демо смешивается с реальными данными | Раздельные adapters/environments, explicit mode, никаких prod seeds/fallback |
| Подмена утверждённых строк или фото | DB immutability, append-only audit, private versioned files, freeze monthly snapshot |
| Двойной учёт или потеря реальных повторных работ | Stable IDs, unique constraints, incremental/cumulative semantics, source provenance |
| Генерация затирает текст PM | Generated source отдельно от PM edits, versioned diff/confirm regeneration |
| Сетевые ошибки и параллельное редактирование | Optimistic locking, idempotency keys, retry с явным состоянием, conflict UX |
| Неверные Excel/опасные вложения | Parser limits, validation/preview, PM confirmation, private attachments |
| PDF-worker не подходит выбранному hosting | Ранний технический spike, лимиты памяти/времени, управляемые jobs |
| Утечка данных через кеш/ссылки/логи | Auth-aware caching, short-lived URLs, повторная проверка download, logs без содержимого/секретов |
| Нет оригинальных бренд-активов | Получить исходники; до этого использовать нейтральный явно временный layout, не перерисовывать логотип |
| Увеличение стоимости | Не создавать подписки/активировать production, измерять объёмы storage/jobs, отдельно согласовывать платные функции |
